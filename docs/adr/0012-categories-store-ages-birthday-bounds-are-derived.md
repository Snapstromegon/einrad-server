# Categories store ages, birthday bounds are derived

A category stores only its age class: `min_age` and `under_age`, either of which may be empty for an open end. Fractions mean months, so `9.5` is 9 years 6 months. The birthday range is never stored. It is worked out from the competition's determining day wherever it is needed: `from_birthday = determining_day − under_age` (inclusive) and `to_birthday = determining_day − min_age` (exclusive). This happens in the act view in SQL, in `seed` in Rust and in the admin form in TypeScript, and all three give the same result, including a determining day of 29 February. We chose this so that changing the determining day moves every category without touching any rows, and so that an exported competition file carries over to the next season unchanged. Stored dates went stale on both counts, and #299's `move_birthday_bound` only patched over that.

Explicit `from_birthday` / `to_birthday` are gone from the database, the competition file, the API and the export. An older file or database that still has them is converted once. 1900-01-01 and 9999-12-31 become an open end, and a date that is a whole number of months before the determining day becomes that age. Any other date fails loudly and names the category; it is never rounded. The migration raises that error through a deliberately malformed `json_extract` path rather than `RAISE` in a trigger, because the sqlx-cli in use can't parse the trigger form.
